# Частина 2. AddressSanitizer

Тема: помилки роботи з пам'яттю. Інформація: OSTEP [14. Interlude: Memory API](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-api.pdf) (розділ Common Errors).

## Мета

Навчитися читати звіт AddressSanitizer (ASan) і зрозуміти, чому програма з помилкою пам'яті може «працювати».

## Дано

Шість програм `bug1.c` … `bug6.c`. У кожній рівно одна помилка роботи з пам'яттю. Коментар на початку файлу каже, що програма має надрукувати. `Makefile` збирає їх з ASan (`make`) і без нього (`make plain`).

## Завдання

1. Зберіть і запустіть усі шість:

   ```sh
   cd part2-asan
   make run
   ```

   Команда запускає всі шість програм і повертає ненульовий код, якщо хоча б одна завершилася з помилкою.

2. Для кожного звіту ASan розберіть: тип помилки (перший рядок після `ERROR`), операція і розмір (`READ of size 4`), стек викликів до рядка у вашому файлі (`bug1.c:9`), а для помилок купи ще й де і ким ця пам'ять була виділена або звільнена (блоки `allocated by` / `freed by`).

3. Знайдіть **причину**, а не симптом, і виправте. Виправлення має зберегти призначення програми: вивід має збігатися з коментарем на початку файлу. Видалити `free`, збільшити масив «про запас» або додати `+ 10` до розміру — не виправлення.

4. Переконайтеся, що після виправлення `make run` проходить без повідомлень ASan, зокрема без `LeakSanitizer` наприкінці.

5. Зберіть без ASan і запустіть виправлені й невиправлені версії:

   ```sh
   make plain
   ./bug1-plain
   ```

   Для невиправлених зафіксуйте, що відбувається: правильний вивід, сміття, аварія від glibc (`free(): …`) або segfault. Поясніть, чому поведінка така і чи можна на неї покладатися.

## Підказки

- Компілятор іноді теж бачить помилку: читайте попередження `gcc`. Але він бачить далеко не все.
- Тип `heap-buffer-overflow` з `WRITE of size 18` у виклику `strcpy` означає, що запис довший за виділений блок. Подивіться, скільки виділили і скільки насправді потрібно.
- У `heap-use-after-free` подивіться на порядок дій у циклі: що звільняється і що читається після цього.
- `LeakSanitizer` спрацьовує при виході з програми: пам'ять виділили, а покажчик на неї втратили.
- `double-free`: один і той самий блок звільняють двічі. Хто другий власник покажчика і звідки він узявся?
- Для `stack-buffer-overflow` ASan вказує, у stack frame якої функції лежить масив і на якому зміщенні. Порахуйте індекси.

## Запитання для самоперевірки й захисту

- Чи надрукував `bug1-plain` правильне середнє у вашому запуску? Чому навіть правильний вивід не доводить коректності читання пам'яті?
- Які помилки у ваших запусках без ASan помітила glibc? Чому вона не помітила решту й чи гарантована така сама поведінка в іншому запуску?
- Чому ASan вмикають під час розробки й тестування, але не в готовій програмі?
- Яких помилок ASan не ловить і чому?
- Чому в C копія структури не копіює «вміст» покажчика? Як та сама ситуація виглядає в C# зі `struct`, у якої є поле-масив, і чому там не буває double-free?

# Бонус. Послідовний і випадковий доступ до пам'яті

Виконується після частин 4–5. Інформація: OSTEP [19. Paging: Faster Translations (TLBs)](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf) (домашнє завдання в кінці розділу — саме цей дослід), [22. Beyond Physical Memory: Policies](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys-policy.pdf).

## Мета

Порівняти швидкість послідовного й випадкового доступу до пам'яті та пояснити вплив кешів процесора, TLB і підкачки.

## Дано

`access.c`: виділяє масив заданого розміру і робить 64 мільйони читань у трьох режимах:

- `seq`: підряд;
- `stride`: кожне наступне читання на 4096 байт далі, тобто з нової сторінки, але передбачувано;
- `rand`: випадковий індекс.

Друкує час, наносекунди на один доступ і кількість major faults за час вимірювання. Збирається з `-O2`, щоб зменшити накладні витрати циклу. Вимір охоплює також обчислення індексів, а в `rand` — генерацію випадкових чисел, тому це час усього циклу, а не чиста затримка читання з пам'яті.

## Завдання

1. Три режими на одному розмірі:

   ```sh
   for m in seq stride rand; do ./bonus-access/access $m 64; done
   ```

2. Випадковий доступ на зростаючих розмірах від 1 до 256 МіБ:

   ```sh
   for s in 1 2 4 8 16 32 64 128 256; do ./bonus-access/access rand $s; done
   ```

   Не перевищуйте чверть RAM вашої VM. Побудуйте таблицю або графік «розмір → нс/доступ» і відзначте сходинки, якщо вони є.

3. Поясніть результати:
   - **Кеші**: порівняйте зміни на графіку `rand` із розмірами кешів свого процесора. Як розмір кешів впливає на час доступу?
   - **TLB**: порівняйте `seq` і `stride` на 64 МіБ. За сторінок 4 КіБ `stride` щоразу переходить до іншої сторінки. Чому при `stride` може бути більше промахів TLB, ніж при `seq`? Що змінилося б, якби сторінки були 2 МіБ, а крок лишився 4 КіБ?
   - **Підкачка**: перевірте, що буде, якщо масив не вміщується в пам'ять, яку ядро дає процесу. Для цього потрібен swap, а у VM його зазвичай немає, тому спершу створіть тимчасовий файл підкачки:

     ```sh
     sudo fallocate -l 512M /swapfile-lab && sudo chmod 600 /swapfile-lab
     sudo mkswap /swapfile-lab && sudo swapon /swapfile-lab
     ```

     Запустіть програму двічі: звичайно і з обмеженням у 56 МіБ, тобто меншим за масив у 64 МіБ. `systemd-run ... -p MemoryMax=56M` запускає програму, якій ядро дає не більше 56 МіБ RAM:

     ```sh
     ./bonus-access/access seq 64
     systemd-run --user --scope -q -p MemoryMax=56M ./bonus-access/access seq 64
     ```

     Порівняйте нс/доступ і major faults у двох рядках виводу. Чому другий запуск повільніший і звідки в нього major faults, якщо програма не читає файлів?

     Після досліду видаліть файл підкачки:

     ```sh
     sudo swapoff /swapfile-lab && sudo rm /swapfile-lab
     ```

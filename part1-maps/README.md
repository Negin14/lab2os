# Частина 1. Адреси та /proc/self/maps

Тема: адресний простір процесу. Інформація: OSTEP [13. The Abstraction: Address Spaces](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf), [14. Interlude: Memory API](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-api.pdf).

## Мета

Побачити, що адреси змінних не випадкові: кожна належить до області, яку ядро показує в `/proc/<pid>/maps`.

## Дано

`maps.c`: програма друкує адреси `main` і глобальної змінної, а потім вміст власного `/proc/self/maps`.

## Завдання

1. Зберіть і запустіть: `make` у каталозі `lab2`, потім `./part1-maps/maps`. Подивіться на вивід. Кожен рядок maps: діапазон адрес, права (`r`, `w`, `x`, `p` приватне / `s` спільне), зміщення у файлі, пристрій, inode, шлях або назва області.

2. Виконайте **TODO 1–3** у `maps.c`. Для TODO 2 у вас мають вийти: рядки виконуваного файлу (шлях до нього в кінці рядка) з правами `r-xp` для коду і `rw-p` для даних, `[heap]`, `[stack]` та анонімне відображення без імені.

3. Запустіть програму ще раз. Що змінилося, що ні? Потім:

   ```sh
   setarch -R ./part1-maps/maps
   cat /proc/sys/kernel/randomize_va_space
   ```

4. Подивіться розмір стека і поріг, за яким `malloc` переходить на `mmap`:

   ```sh
   ulimit -s
   man mallopt   # знайдіть M_MMAP_THRESHOLD
   ```

## Запитання для самоперевірки й захисту

- Чому виконуваний файл займає кілька рядків maps з різними правами? Що буде, якщо записати за адресою `main`?
- Чи потрапили `global_initialized` і `global_uninitialized` в один рядок maps? Які права доступу мають області, де вони розташовані?
- Чому `big` опинився не в `[heap]`, а в окремому анонімному відображенні? Що зміниться, якщо зменшити його до 64 КіБ?
- Навіщо ядро змінює адреси між запусками? Які адреси змінюються, а які ні?
- Чому `[stack]` у maps займає лише ~130 КіБ, хоча `ulimit -s` каже 8 МіБ?
- `/proc/self/maps` показує віртуальні чи фізичні адреси? Чи може програма дізнатися фізичну адресу своєї змінної?
